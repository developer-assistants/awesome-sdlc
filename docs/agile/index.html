Agile SDLC and SDLC vs Agile

Agile does not replace the Software Development Life Cycle. It compresses planning, design, coding, testing, and release into repeating one- to three-week loops.

How SDLC and Agile relate

A frequent interview misconception treats SDLC and Agile as opposites. SDLC is the universal set of activities required to build and operate software. Agile is an iterative methodology for scheduling those activities so teams validate assumptions with real users early instead of waiting until the end of a six-month build.

Definition of Ready (DoR) vs Definition of Done (DoD)

Two lightweight checklists keep Agile sprints from stalling. Definition of Ready verifies that a story is clear enough to start: user problem stated, acceptance criteria testable, dependencies identified, and mocks attached if UI changes. Definition of Done verifies that a story is ready to ship: code reviewed, unit and integration tests passing in CI, security checks clean, documentation updated, and verified in staging.

Useful Agile engineering metrics

  • Cycle time: elapsed time from starting a ticket to deploying it to production. Lower cycle time exposes bottlenecks faster than story-point velocity.
  • Escaped defects: bugs found in production instead of during sprint testing.
  • Work-in-progress (WIP): number of open tasks per engineer. High WIP signals context switching and stalled code reviews.
  • Sprint predictability: ratio of completed commitments to planned sprint scope over a rolling 3-sprint window.

Common Agile anti-patterns

Teams lose the benefits of Agile when they run "mini-Waterfalls" inside sprints (coding for 8 days and dumping everything on QA on day 9), use story points to compare individual developers, or skip architecture design under the excuse of moving fast. Keeping stories small and automating tests inside CI solves most of these traps.
