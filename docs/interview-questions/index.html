Common SDLC interview questions

1. What are the seven phases of SDLC in order?

Planning, requirements analysis, system design, implementation, testing, deployment, and maintenance. Some teams merge planning and requirements into a six-phase list.

2. What is the difference between verification and validation?

Verification checks whether the software matches its specification ("did we build the product right?") using reviews, static analysis, and unit/integration tests. Validation checks whether the software solves the user problem ("did we build the right product?") through user acceptance testing and beta feedback.

3. When would you choose Waterfall over Agile?

Choose Waterfall when requirements are fixed and verified up front, external compliance demands signed stage gates, or the work is a fixed-scope vendor contract where mid-project scope changes are disallowed.

4. What is shift-left testing?

Shift-left testing moves quality checks earlier in the lifecycle: reviewing requirements for testability, writing automated unit and contract tests during development, and running security scanners on every pull request rather than waiting for a final QA stage.

5. What is a Requirements Traceability Matrix (RTM)?

An RTM is a table linking every requirement ID to its design component, test cases, and release verification result. It proves that no requirement was missed and no extra untested scope slipped in.

6. How do CI/CD pipelines fit into SDLC?

Continuous Integration automates the boundary between implementation and testing by building and testing every commit. Continuous Delivery and Deployment automate packaging, staging verification, and production rollout with fast rollbacks.

7. What are the four types of software maintenance?

Corrective (bug fixes), adaptive (environment, OS, or dependency updates), perfective (performance and UX improvements), and preventive (refactoring and technical debt reduction).

8. What is the main weakness of the V-Model?

Like Waterfall, the V-Model assumes requirements stay stable. If product needs change halfway through implementation, both specification documents and paired test plans have to be rewritten.
