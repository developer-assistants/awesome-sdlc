The 7 phases of the software development life cycle

Every phase takes a concrete input, produces a verifiable artifact, runs a security check, and closes with an explicit exit gate.

1. Planning

Planning answers whether a project should be built now, what it will cost, and what happens if dependencies slip. Engineers evaluate technical feasibility (TELOS: Technical, Economic, Legal, Operational, Schedule) rather than guessing dates in a vacuum.

Concrete example: before building a self-serve billing portal, the engineering manager estimates six weeks for two backend engineers and one frontend engineer, confirms payment gateway transaction fees, verifies PCI SAQ-A scope so raw card numbers never touch company servers, and explicitly defers multi-currency invoicing to phase two.

Common pitfall: skipping explicit non-goals. When non-goals are unwritten, every stakeholder assumes their edge case is included in v1.

2. Requirements analysis

Product and engineering convert business objectives into testable specifications. Functional requirements describe observable system behavior ("export filtered ledger rows to CSV within 5 seconds for up to 50,000 rows"). Non-functional requirements specify operational boundaries: availability (99.9% monthly uptime allows 43.8 minutes of downtime), p95 latency under 250ms, GDPR deletion within 30 days, and WCAG 2.1 AA accessibility.

Common pitfall: writing vague adjectives like "fast", "scalable", or "user-friendly" without numbers that QA can test.

3. System design

Tech leads translate requirements into concrete components: database schemas, indexing strategies, caching tiers, message queues, authentication flows, and external API contracts. Teams document major trade-offs in short Architecture Decision Records (ADRs) committed inside the repository so future engineers understand why PostgreSQL was chosen over a document store or why a monolith beat microservices.

Common pitfall: designing only the happy path and ignoring timeouts, duplicate webhooks, partial failures, and rate limits. Start from our Architecture Design Doc and ADR templates.

4. Implementation

Developers break design components into small, reviewable pull requests (ideally under 300 lines of diff). Every commit triggers automated Continuous Integration: formatting, linting, strict type checks, unit tests, secret scanning, and static security analysis. Keeping branches short-lived (trunk-based development) avoids painful merge conflicts.

Common pitfall: letting pull requests sit unreviewed for days or batching unrelated refactors with feature changes.

5. Testing

Testing verifies that the software meets specifications (verification) and solves the user problem (validation). Teams layer tests using the testing pyramid: thousands of fast unit tests (milliseconds), targeted integration tests against real database containers (seconds), and a focused suite of end-to-end tests covering revenue-critical user paths. Before major launches, teams also run load tests at 2x expected peak traffic and verify role-based access control.

Common pitfall: treating QA as a manual bottleneck at the end of a release instead of automating regression checks in CI.

6. Deployment

Deployment promotes an immutable, tested build artifact from staging to production. For zero-downtime releases, teams use expand-and-contract database migrations: first add new nullable columns and deploy code that writes to both old and new fields; backfill historical rows; switch reads; and drop the old column in a later release. Traffic shifts via canary rollouts (5% -> 25% -> 100%) or blue-green switches so rollbacks take seconds instead of hours.

Common pitfall: running destructive schema drops inside the same deploy as application code, making rollback impossible.

7. Maintenance and operations

Most production software spends 70% to 80% of its total cost of ownership in maintenance. ISO/IEC 14764 groups maintenance into four types: corrective (fixing production bugs), adaptive (keeping up with OS, browser, or third-party API changes), perfective (improving latency, cost efficiency, or UX), and preventive (refactoring, dependency upgrades, and retiring dead code). When incidents occur, teams run blameless post-mortems that turn outage timelines into concrete engineering safeguards.

Measuring SDLC health with DORA metrics

Rather than measuring lines of code or raw story points, high-performing engineering teams track the four DORA (DevOps Research and Assessment) metrics to balance delivery speed against production stability:
