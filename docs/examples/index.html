Real-world SDLC examples

How the seven SDLC phases look in practice across three everyday software engineering projects.

Example 1: Adding subscription billing to a B2B SaaS app (Agile)

A six-person SaaS team wants to move from manual PDF invoices to automated card billing.

  1. Planning: Target a four-week launch for monthly and annual plans; defer enterprise wire transfers to Q3.
  2. Requirements: Users upgrade or downgrade plans self-serve; failed charges retry three times over seven days; webhook events must be idempotent.
  3. Design: Store subscription state in a local PostgreSQL table synced from Stripe webhooks; never store raw card numbers.
  4. Implementation: Build checkout session endpoints, webhook signature verification, and billing settings UI in two two-week sprints.
  5. Testing: Replay Stripe CLI test events for payment succeeded, failed, and chargeback scenarios in staging.
  6. Deployment: Enable the billing tab for 10% of workspaces via feature flag, verify webhook logs, then open to 100%.
  7. Maintenance: Alert on webhook 5xx errors and reconcile subscription counts nightly.

Example 2: Shipping a public rate-limited REST API (Iterative)

A logistics company exposes shipment tracking endpoints to external partners.

  1. Planning: Define a 99.95% uptime SLO and assign a dedicated API platform squad.
  2. Requirements: OAuth 2.0 client credentials, 120 requests per minute per key, OpenAPI 3.1 docs, and JSON error codes following RFC 9457.
  3. Design: Put an API gateway in front of a read-replica database with Redis token-bucket rate limiting.
  4. Implementation: Generate server stubs from the OpenAPI contract and write contract tests before wiring resolvers.
  5. Testing: Run k6 load tests at 3x expected peak traffic and verify 429 Retry-After headers.
  6. Deployment: Release v1 behind a versioned path (/v1/shipments) with canary traffic routing.
  7. Maintenance: Publish deprecation headers six months before retiring any field.

Example 3: Firmware update for a medical infusion pump (V-Model)

An embedded systems team updates dosage-calculation firmware under FDA Class II oversight.

  1. Planning: Freeze scope, assign safety officer, and schedule formal external audit dates.
  2. Requirements: Baseline every dosage boundary and alarm trigger in a traceable SRS document.
  3. Design: Map hardware interrupts, memory bounds, and fail-safe shutdown states.
  4. Implementation: Write MISRA-C compliant code with mandatory dual-engineer code reviews.
  5. Testing: Run unit, hardware-in-the-loop integration, system, and clinical acceptance tests linked 1-to-1 to the SRS.
  6. Deployment: Sign firmware binaries with hardware security modules and distribute via controlled hospital updates.
  7. Maintenance: Track field telemetry and maintain long-term audit archives.
