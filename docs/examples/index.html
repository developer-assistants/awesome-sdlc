Real-world SDLC examples

How the seven SDLC phases look in day-to-day engineering across four distinct product types, from startups to regulated hardware.

Example 1: Adding subscription billing to a B2B SaaS app (Agile)

Team: 2 backend engineers, 1 frontend engineer, 1 product manager. Timeline: 4 weeks (two 2-week sprints).

  1. Planning: Target self-serve monthly and annual card plans; defer enterprise wire transfers and multi-currency invoicing to Q3.
  2. Requirements: Workspaces can upgrade or downgrade mid-cycle with proration; failed charges retry three times over seven days; Stripe webhooks must be idempotent.
  3. Design: Store subscription status in a local PostgreSQL table synced via webhooks; never store raw PAN card data so PCI compliance stays at SAQ-A; document schema in an ADR.
  4. Implementation: Build checkout session endpoints, HMAC webhook signature verification, and billing settings UI in small PRs with unit tests.
  5. Testing: Replay Stripe CLI test events for payment succeeded, failed, disputed, and out-of-order webhook delivery in staging.
  6. Deployment: Enable the billing tab for 10% of workspaces behind a feature flag, inspect webhook logs for 48 hours, then roll out to 100%.
  7. Maintenance: Alert on webhook 5xx rates above 0.5% and run a nightly reconciliation job against Stripe's API.

Example 2: Shipping a public rate-limited REST API (Iterative)

Team: 4 backend engineers, 1 SRE, 1 QA engineer. Timeline: 8 weeks across two milestones.

  1. Planning: Commit to a 99.95% monthly uptime SLO and assign on-call rotation before onboarding external partners.
  2. Requirements: OAuth 2.0 client credentials, 120 requests per minute per API key, OpenAPI 3.1 reference docs, and structured RFC 9457 error responses.
  3. Design: Place an API gateway in front of read-replica PostgreSQL nodes with Redis token-bucket rate limiting and cursor-based pagination.
  4. Implementation: Generate TypeScript/Go contract tests directly from the OpenAPI file so handler changes cannot break response schemas silently.
  5. Testing: Execute k6 load tests at 3x expected peak traffic (1,500 RPS), verify HTTP 429 Retry-After headers, and test Redis failover.
  6. Deployment: Release under /v1/shipments using canary traffic splits (5%, 25%, 100%) with automated rollback if p95 latency exceeds 300ms.
  7. Maintenance: Publish Sunset and Deprecation HTTP headers at least six months before retiring any field.

Example 3: Firmware update for a medical infusion pump (V-Model)

Team: 8 embedded C engineers, 4 verification engineers, 1 regulatory quality lead. Timeline: 6 months.

  1. Planning: Freeze scope, assign safety officer under IEC 62304, and lock external audit dates.
  2. Requirements: Baseline every dosage limit, occlusion sensor threshold, and audible alarm latency in a Requirements Traceability Matrix (RTM).
  3. Design: Map hardware interrupts, deterministic memory bounds (zero dynamic heap allocation), and fail-safe shutdown states.
  4. Implementation: Write MISRA-C compliant firmware with mandatory dual-engineer code reviews and static analysis.
  5. Testing: Execute unit tests, hardware-in-the-loop (HIL) integration tests, system soak tests (72 hours continuous), and clinical acceptance tests mapped 1-to-1 to the RTM.
  6. Deployment: Cryptographically sign firmware images using hardware security modules and distribute via controlled hospital service updates.
  7. Maintenance: Retain full build artifacts, compiler versions, and field telemetry for regulatory audit windows.

Example 4: Offline-first mobile field inspection app (Agile + Phased Rollout)

Team: 2 mobile engineers, 1 backend engineer, 1 QA engineer. Timeline: 6 weeks.

  1. Planning: Support iOS 16+ and Android 12+, account for 3-day App Store review buffers, and scope offline photo queues.
  2. Requirements: Technicians complete inspection forms with zero cellular signal; queued uploads resume automatically on reconnect without duplicate records.
  3. Design: Use local SQLite with client-generated UUIDv7 record IDs and an idempotent sync endpoint; store auth tokens in Keychain / Android Keystore.
  4. Implementation: Build screens with dynamic font sizing, background upload workers, and automated signed builds in CI.
  5. Testing: Test on physical low-end Android and iOS devices under airplane mode, 3G throttling, and mid-upload app kills; run TestFlight beta with 15 field technicians.
  6. Deployment: Ship via staged store rollout (10% -> 50% -> 100%) while watching Crashlytics crash-free session rates (target above 99.6%).
  7. Maintenance: Update SDK targets annually for Apple and Google store policy deadlines and retire legacy sync APIs safely.

Example CI quality gate (GitHub Actions)

Automating Phase 4 and Phase 5 checks in CI keeps code quality consistent across every pull request:

name: SDLC Pull Request Gate
on: [pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '22' }
      - run: npm ci
      - run: npm run lint
      - run: npm run typecheck
      - run: npm test -- --coverage
      - run: npm audit --audit-level=high
